# QXDM Log Analyser: Master Architectural Blueprint

## 1. Executive Summary
This document defines the "North Star" architecture for the QXDM Log Analyser. It transitions the system from a fragile, heavily-regex-dependent Python monolith into a robust, **Agent-Centric Architecture**. 

By adopting a **"Dumb Pipe, Smart Agent"** philosophy, we separate deterministic data movement (Python) from probabilistic reasoning and pattern recognition (LLM Agents). This eliminates "Regex Hell," solves Out-Of-Memory (OOM) scaling issues, and allows the system to adapt to any client's specific log formatting automatically without code changes.

---

## 2. Core Architectural Philosophy
*   **Python is the Dumb Pipe:** Python scripts are strictly responsible for file I/O, chunking, memory-safe streaming, and basic text splitting. They do not attempt to "understand" telecom protocols or perform complex analysis.
*   **The Agent is the Brain:** LLM Agents handle all cognitive tasks: deducing log schemas from raw text, identifying anomalies, correlating cross-RAT (LTE/5G) events, and generating Root Cause Analysis (RCA) reports.
*   **Raw Preservation:** The system never destroys or heavily transforms the original client data. Raw log blocks are preserved exactly as written, ensuring the Agent always has ground-truth data to inspect.
*   **Chronological Infallibility:** Time-series ordering relies on mathematically sound Epoch integers and global sequence IDs, completely bypassing the unreliability of string-based timestamp sorting.

---

## 3. System Components

The system is divided into four distinct components.

### 3.1 The File Watcher & Orchestrator (`batch_processor.py`)
**Role:** The deterministic traffic cop.
*   **Responsibilities:**
    *   Monitors input directories for new `.txt` log chunks.
    *   Implements "stability windows" (waits for file size to stop changing) to prevent reading mid-write.
    *   Groups files into logical `test_id` runs based on filename conventions.
    *   Moves files to `processed/` or `failed/` directories.
*   **What it DOES NOT do:** It does not parse the contents of the files. It only manages the lifecycle of the files on the filesystem.

### 3.2 The Configurator Agent (LLM)
**Role:** The Schema Deduction Engine.
*   **Trigger:** Activated by the Orchestrator when a *new* log format or client profile is detected.
*   **Mechanism:** 
    *   The Agent is given a tool to stream the raw text of the first chunk line-by-line until it identifies the first valid log block (the "datetime line").
    *   It analyzes the structure of that block to deduce the regex required to split blocks, and the specific `strptime` format required to parse the timestamp.
*   **Output:** Generates a lightweight `splitter_config.json` for this specific `test_id` or client profile.
    ```json
    {
      "profile_id": "client_xyz_5g",
      "block_delimiter_regex": "^\\d{4}-\\d{2}-\\d{2}",
      "timestamp_extraction_regex": "^(\\d{4}-\\d{2}-\\d{2} \\d{2}:\\d{2}:\\d{2}\\.\\d{3})",
      "strptime_format": "%Y-%m-%d %H:%M:%S.%f"
    }
    ```

### 3.3 The Raw Block Ingestor (`indexer.py`)
**Role:** The High-Performance Loader.
*   **Responsibilities:**
    *   Reads the `splitter_config.json` generated by the Configurator Agent.
    *   Streams the 250MB+ files line-by-line (zero OOM risk).
    *   Splits the stream into discrete "Blocks" using the Agent's `block_delimiter_regex`.
    *   Extracts the timestamp string and converts it to an **Epoch Millisecond Integer** using the Agent's `strptime_format`.
    *   Assigns a strictly incremental `global_sequence_id` to every block.
*   **Storage:** Writes the data into the **Universal Log Store** (SQLite). It stores the raw text exactly as provided by the client.

### 3.4 The Analyst Agent (The "Skill")
**Role:** The Telecom RCA Expert.
*   **Trigger:** Activated by the Orchestrator once the Ingestor finishes processing a `test_id`.
*   **Mechanism:** The Agent connects to the SQLite database and uses a set of predefined Python tools to investigate the logs. It searches for keywords, reads raw blocks, correlates timestamps, and identifies 3GPP spec violations (e.g., missing T3346 timers, off-raster redirects).
*   **Output:** Writes a structured JSON summary into the `test_run_analysis` table, containing the verdict, primary root cause, and executive summary.

## 4. Database Schema: The Universal Log Store

The database is stripped of complex, protocol-specific tables (`nas_events`, `rf_kpis`, `events`). Instead, it uses a unified, high-performance schema optimized for Full-Text Search (FTS5).

### 4.1 Core Tables

**`test_runs`** (Metadata & Status)
```sql
CREATE TABLE test_runs (
    test_id TEXT PRIMARY KEY,
    status TEXT DEFAULT 'INDEXING', -- WAITING, INDEXING, ANALYZING, READY, FAILED
    chunk_count INTEGER,
    started_at TEXT,
    completed_at TEXT
);
```

**`log_blocks`** (The Raw Data)
```sql
CREATE TABLE log_blocks (
    id INTEGER PRIMARY KEY,
    test_id TEXT NOT NULL,
    global_sequence_id INTEGER NOT NULL, -- Guarantees chronological order
    timestamp_raw TEXT,                  -- The client's exact original string
    timestamp_epoch_ms INTEGER,          -- The mathematically sortable integer
    msg_code TEXT,                       -- Quick filter (e.g., "0x1FE7") if easily extractable
    raw_text TEXT NOT NULL               -- The exact, untouched block content
);
CREATE INDEX idx_sequence ON log_blocks(test_id, global_sequence_id);
CREATE INDEX idx_epoch ON log_blocks(test_id, timestamp_epoch_ms);
```

**`log_blocks_fts`** (The Agent's Search Engine)
```sql
-- SQLite FTS5 virtual table for lightning-fast keyword searches by the Agent
CREATE VIRTUAL TABLE log_blocks_fts USING fts5(
    raw_text, 
    content='log_blocks', 
    content_rowid='id'
);
```

**`test_run_analysis`** (The Agent's Output)
```sql
CREATE TABLE test_run_analysis (
    test_id TEXT PRIMARY KEY,
    overall_health TEXT, -- PASS, DEGRADED, CRITICAL_FAILURE
    primary_issue TEXT,  -- e.g., "5GC NAS Congestion Loop"
    executive_summary TEXT,
    detailed_findings_json TEXT -- Structured data for future dashboard
);
```

## 5. Agent Tooling Interface

To interact with the database, the Analyst Agent is provided with the following deterministic Python tools:

1.  **`search_blocks(query: str, limit: int = 50) -> list[dict]`**
    *   *Description:* Uses SQLite FTS5 to find blocks containing specific keywords (e.g., `"RRC Release"`, `"Cause=22"`).
    *   *Returns:* A list of dictionaries containing `global_sequence_id`, `timestamp_raw`, and `raw_text`.
2.  **`get_block_context(sequence_id: int, window: int = 10) -> list[dict]`**
    *   *Description:* Retrieves the exact sequence of blocks surrounding a specific event (e.g., 10 blocks before and after an RRC Release).
3.  **`count_pattern(regex_pattern: str) -> int`**
    *   *Description:* Runs a fast SQLite regex count to determine how many times a specific error code or message appears in the test run.
4.  **`save_analysis(verdict: str, summary: str, findings: dict)`**
    *   *Description:* Writes the final RCA report to the `test_run_analysis` table.

---

## 6. End-to-End Execution Flow

1.  **Ingestion:** The Orchestrator detects `RUN123_chunk_001.txt` through `004.txt` in the input folder.
2.  **Configuration:** The Orchestrator notices this is a new client format. It spins up the **Configurator Agent**, which reads the first few lines of chunk 001, deduces the schema, and saves `client_xyz_config.json`.
3.  **Loading:** The **Raw Ingestor** reads the config, streams all 4 chunks into memory-safe batches, splits the text into blocks, converts timestamps to Epoch integers, and writes them to `log_blocks` and `log_blocks_fts`.
4.  **Analysis:** The Orchestrator spins up the **Analyst Agent**. The Agent uses `search_blocks("Registration Reject")` to find NAS failures, reads the surrounding blocks using `get_block_context`, realizes the T3346 timer is missing, and uses `save_analysis` to write the RCA to the database.
5.  **Completion:** The Orchestrator updates `test_runs.status` to `'READY'`.

## 7. Future Considerations (The Dashboard)

Because the database now stores the Agent's high-level reasoning in `test_run_analysis` and the raw data in a standardized `log_blocks` format, the future Dashboard will be incredibly simple to build:

*   **Overview Page:** Simple SQL queries against `test_runs` and `test_run_analysis` (e.g., "Show me all tests from today with `overall_health = CRITICAL_FAILURE`").
*   **Drill-Down Page:** When a user clicks a failed test, the dashboard queries `log_blocks` using the `global_sequence_id` ranges identified by the Agent, displaying the exact raw text snippets that caused the failure.
*   **No Backend Logic:** The dashboard will require zero Python analysis logic. It will purely be a visualization layer over the SQLite database.
